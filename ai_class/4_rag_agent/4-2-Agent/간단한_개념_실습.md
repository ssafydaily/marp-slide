# LangChain Tool 함수 작성 가이드

- LangChain tool은 `@tool` 데코레이터로 만든다. 
- 핵심은 **LLM이 도구를 선택하고 호출하는 데 필요한 정보(이름, 설명, 파라미터 스키마)가 함수 자체에서 자동으로 추출된다**는 점이다.
- **docstring** 과 **타입 힌트** 가 단순 주석이 아니라 **실제로 LLM에게 전달되는 스펙**이 된다.

-----------------------

## 작성 예시 

```python
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """지정한 도시의 현재 날씨 정보를 조회합니다.

    Args:
        city: 날씨를 조회할 도시 이름 (예: "서울", "부산")

    Returns:
        날씨 요약 문자열
    """
    # 실제로는 API 호출 등을 수행
    return f"{city}의 날씨는 맑음, 25도입니다."
```

---------------


## 주의할 점들

### Docstring은 필수, 그리고 "설명"이어야 함
- docstring이 곧 tool의 `description`이 되어 **LLM이 "이 도구를 언제 써야 하는지" 판단하는 근거** 가 된다.
- docstring이 없으면 에러가 나거나(버전에 따라 다름), 있어도 애매하면 LLM이 엉뚱한 상황에 도구를 호출한다.
- "이 함수는 X를 한다"가 아니라 **"언제, 무엇을 위해 쓰는 도구인지"**를 명확히 작성한다.

------------

```python
# 나쁜 예 - 너무 짧고 모호함
@tool
def search(query: str) -> str:
    """검색한다."""
    ...

# 좋은 예 - 용도와 사용 시점이 명확
@tool
def search_company_docs(query: str) -> str:
    """사내 문서 저장소에서 키워드로 문서를 검색합니다.
    일반적인 웹 검색이 아니라 내부 정책, 매뉴얼 등을 찾을 때 사용하세요.

    Args:
        query: 검색할 키워드나 질문
    """
    ...
```

### 타입 힌트를 반드시 명시
- 파라미터 타입이 **JSON Schema** 로 변환되어 LLM에게 전달된다.
- 타입이 없으면 스키마가 부정확해지고, LLM이 잘못된 타입의 값을 넣어 호출할 수 있다.

```python
from typing import Literal

@tool
def convert_currency(amount: float, from_currency: str, to_currency: Literal["USD", "KRW", "EUR"]) -> str:
    """통화를 변환합니다.

    Args:
        amount: 변환할 금액
        from_currency: 원래 통화 코드
        to_currency: 변환할 통화 코드 (USD, KRW, EUR 중 하나)
    """
    ...
```

### 함수 이름도 신경 쓰기
- 함수 이름이 곧 tool의 `name`이 됩니다. 동사+명사 형태로 역할을 드러나게 작성한다. (`get_weather` O, `weather` △, `func1` X)

### 에러를 그대로 던지지 말고 처리해서 반환
- 도구 안에서 예외가 그대로 터지면 그래프 실행이 죽거나 예상치 못한 흐름이 된다.
- LLM이 다음 판단을 할 수 있도록 에러 상황도 문자열로 알려주는 게 안전한다.

```python
@tool
def divide(a: float, b: float) -> str:
    """두 숫자를 나눕니다."""
    try:
        return str(a / b)
    except ZeroDivisionError:
        return "오류: 0으로 나눌 수 없습니다."
```

### 복잡한 입력은 Pydantic 스키마로 명시 (`args_schema`)

- 파라미터가 많거나 검증이 필요하면 Pydantic 모델을 별도로 정의해서 각 필드에 `Field(description=...)`로 설명을 달아주는 게 훨씬 안정적이다.

```python
from pydantic import BaseModel, Field

class SendEmailInput(BaseModel):
    to: str = Field(description="수신자 이메일 주소")
    subject: str = Field(description="이메일 제목")
    body: str = Field(description="이메일 본문 내용")

@tool("send_email", args_schema=SendEmailInput)
def send_email(to: str, subject: str, body: str) -> str:
    """이메일을 발송합니다. 사용자가 명시적으로 메일 전송을 요청했을 때만 사용하세요."""
    return f"{to}에게 이메일을 보냈습니다."
```
-------------

### 반환값은 문자열(또는 직렬화 가능한 값)로
- LLM은 결과를 다시 텍스트로 읽는다.
- 복잡한 객체를 그대로 반환하면 이후 처리에서 문제가 될 수 있다.
- 문자열이나 JSON 직렬화 가능한 형태로 반환하는 게 안전한다.

## 3. 작성한 도구를 직접 확인하는 코드

`@tool`이 자동으로 만들어준 스펙(name, description, args 스키마)을 아래처럼 눈으로 확인할 수 있습니다.

```python
print("이름:", get_weather.name)
print("설명:", get_weather.description)
print("파라미터 스키마:", get_weather.args)

# 실제 호출 테스트 (LLM 없이 직접 invoke)
result = get_weather.invoke({"city": "서울"})
print("실행 결과:", result)
```

출력 예시:
```
이름: get_weather
설명: 지정한 도시의 현재 날씨 정보를 조회합니다.
파라미터 스키마: {'city': {'title': 'City', 'type': 'string'}}
실행 결과: 서울의 날씨는 맑음, 25도입니다.
```

## LLM에 실제로 바인딩해서 tool selection 확인

도구 자체가 잘 작성됐는지는 결국 **LLM이 올바른 상황에서 올바르게 호출하는지**로 검증하는 게 가장 확실합니다.

```python
from langchain_openai import ChatOpenAI  # 사용 중인 모델로 교체 가능

llm = ChatOpenAI(model="gpt-4o-mini")
llm_with_tools = llm.bind_tools([get_weather])

response = llm_with_tools.invoke("서울 날씨 어때?")
print(response.tool_calls)
```

`response.tool_calls`를 보면 LLM이 어떤 도구를, 어떤 인자로 호출하려고 했는지 확인할 수 있습니다. 여기서 도구 이름/인자가 의도와 다르게 나온다면 대부분 **docstring이 모호하거나 파라미터 설명이 부족한 경우**입니다.

```
[{'name': 'get_weather', 'args': {'city': '서울'}, 'id': '...'}]
```
