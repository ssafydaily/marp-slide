# 데이터베이스의 정의

| 정의 | 설명 |
| --- | --- |
| 통합된 데이터 (Integrated) | 중복을 최소화한 데이터의 모임 |
| 저장된 데이터 (Stored) | 컴퓨터가 접근할 수 있는 저장 매체에 저장 |
| 운영 데이터 (Operational) | 조직의 업무 수행에 반드시 필요한 데이터 |
| 공용 데이터 (Shared) | 여러 응용 시스템이 공동으로 소유하고 유지 |

데이터베이스의 특징

- 실시간 접근성, 계속적인 변화, 동시 공용, 내용에 의한 참조

# DBMS

사용자와 데이터베이스 사이에서 데이터베이스를 관리해 주는 소프트웨어.

| 필수 기능 | 설명 | 관련 언어 |
| --- | --- | --- |
| 정의 기능 | 데이터의 타입과 구조, 제약조건을 명시 | DDL |
| 조작 기능 | 검색, 삽입, 삭제, 갱신 수단 제공 | DML |
| 제어 기능 | 무결성, 보안, 권한, 병행 제어 | DCL |

| 장점 | 단점 |
| --- | --- |
| 데이터 중복 최소화, 독립성 확보 | 전문가 부족, 비용 증가 |
| 일관성·무결성·보안 유지 | 백업과 회복이 복잡 |
| 데이터 공유, 표준화 | 시스템이 복잡 |

# 스키마

데이터베이스의 구조와 제약조건에 대한 명세.

| 스키마 | 관점 | 설명 |
| --- | --- | --- |
| 외부 스키마 | 사용자 | 사용자나 응용 프로그램이 보는 논리적 구조. 여러 개 존재 |
| 개념 스키마 | 조직 전체 | 데이터베이스 전체의 논리적 구조. 하나만 존재 |
| 내부 스키마 | 물리적 저장 장치 | 실제 저장될 레코드의 형식, 저장 방법 |

- 개념 스키마에는 개체 간의 관계, 제약조건, 접근 권한, 보안, 무결성 규칙이 들어간다
- 단순히 "스키마" 라고 하면 개념 스키마를 가리킨다
- 뷰(3단계)는 외부 스키마를 구현하는 수단이다

---

# 데이터 독립성

| 독립성 | 설명 |
| --- | --- |
| 논리적 독립성 | 개념 스키마가 바뀌어도 외부 스키마(응용 프로그램)는 영향을 받지 않는다 |
| 물리적 독립성 | 내부 스키마가 바뀌어도 개념 스키마와 응용 프로그램은 영향을 받지 않는다 |

```
외부 스키마 ─┐
외부 스키마 ─┼─ (논리적 독립성) ─ 개념 스키마 ─ (물리적 독립성) ─ 내부 스키마
외부 스키마 ─┘
```

- 인덱스를 추가해도 SQL 을 고칠 필요가 없다 → 물리적 독립성
- 테이블에 컬럼을 추가해도 기존 뷰를 쓰는 프로그램은 그대로 동작한다 → 논리적 독립성

---

# 데이터베이스 설계 단계

| 단계 | 하는 일 |
| --- | --- |
| 요구 조건 분석 | 요구 조건 명세서 작성 |
| 개념적 설계 | 개념 스키마, 트랜잭션 모델링, **E-R 모델** |
| 논리적 설계 | 목표 DBMS 의 논리 스키마 설계, **정규화**, 트랜잭션 인터페이스 설계 |
| 물리적 설계 | 저장 레코드 양식, 접근 경로, **인덱스**, 파티션 설계 |
| 구현 | DDL 로 스키마 생성, 트랜잭션 작성 |

- 순서: 요구 분석 → 개념 → 논리 → 물리 → 구현
- "E-R 다이어그램은 개념, 정규화는 논리, 인덱스는 물리" 로 짝짓는다

# 관계 모델의 용어

| 용어 | 의미 | 실무 용어 |
| --- | --- | --- |
| 릴레이션 (Relation) | 데이터를 표 형태로 표현한 것 | 테이블 |
| 튜플 (Tuple) | 릴레이션의 행 | 행, 레코드 |
| 속성 (Attribute) | 릴레이션의 열 | 열, 컬럼, 필드 |
| 도메인 (Domain) | 한 속성이 가질 수 있는 원자값의 집합 | 타입, CHECK |
| **차수 (Degree)** | **속성의 수** | 컬럼 수 |
| **카디널리티 (Cardinality)** | **튜플의 수** | 행 수 |

- 릴레이션 스키마: 릴레이션의 구조(이름, 속성)
- 릴레이션 인스턴스: 어느 시점의 튜플 집합

---

# 차수와 카디널리티

```sql
SELECT COUNT(*) FROM 학생;   -- 10
DESC 학생;                   -- 5행 (컬럼 5개)
```

| 릴레이션 | 차수 (속성 수) | 카디널리티 (튜플 수) |
| --- | --- | --- |
| 학과 | 3 | 4 |
| 학생 | 5 | 10 |
| 과목 | 4 | 6 |
| 수강 | 3 | 14 |
| 부서 | 3 | 5 |
| 사원 | 8 | 12 |

- 차수(Degree)는 열, 카디널리티는 행. 서로 바꿔 쓰지 않는다
- SELECT 결과에 대해서도 묻는다. `SELECT 학번, 이름 FROM 학생 WHERE 학년 = 1` → 차수 2, 카디널리티 3

---

# 릴레이션의 특징

1. 한 릴레이션의 튜플은 모두 다르다 (중복 튜플 없음)
2. 튜플 사이에는 순서가 없다
3. 속성 사이에는 순서가 없다
4. 속성의 이름은 유일해야 하지만 값은 같을 수 있다
5. 속성의 값은 더 이상 나눌 수 없는 **원자값**이다
6. 튜플은 시간에 따라 삽입·삭제·갱신으로 계속 변한다

- SQL 의 테이블은 기본키가 없으면 중복 행을 허용한다. 이론상의 릴레이션과 다른 점이다
- 순서가 없으므로 `ORDER BY` 가 없는 SELECT 의 결과 순서는 보장되지 않는다

# 키 (Key)

| 키 | 정의 |
| --- | --- |
| 슈퍼키 | 튜플을 유일하게 식별하는 속성 집합. **유일성**만 만족 |
| 후보키 | 유일성과 **최소성**을 모두 만족 |
| 기본키 | 후보키 중에서 선택한 주 키. NULL 과 중복 불가 |
| 대체키 | 후보키 중 기본키가 아닌 것 |
| 외래키 | 다른 릴레이션의 기본키를 참조하는 속성 |

- 유일성: 하나의 키 값으로 하나의 튜플만 식별된다
- 최소성: 키를 이루는 속성 중 하나라도 빼면 유일성이 깨진다
- 포함 관계: 슈퍼키 ⊃ 후보키 = 기본키 + 대체키

---

# 키 — 실습 스키마에서

학과(학과코드, 학과명, 사무실). 학과명에는 UNIQUE 제약이 있다.

| 속성 집합 | 유일성 | 최소성 | 분류 |
| --- | --- | --- | --- |
| {학과코드} | O | O | 후보키 → **기본키** |
| {학과명} | O | O | 후보키 → **대체키** |
| {학과코드, 학과명} | O | X | 슈퍼키 |
| {학과코드, 사무실} | O | X | 슈퍼키 |
| {사무실} | X | - | 키 아님 |

수강(학번, 과목코드, 점수)

- {학번} 만으로는 유일하지 않다. {학번, 과목코드} 가 기본키(복합키)다
- 학번은 학생을, 과목코드는 과목을 참조하는 외래키이기도 하다

# 무결성 (Integrity)

데이터베이스에 저장된 값이 정확하고 일관된 상태를 유지하는 성질.

| 무결성 | 규칙 | SQL 제약 |
| --- | --- | --- |
| 개체 무결성 | 기본키는 NULL 이나 중복 값을 가질 수 없다 | `PRIMARY KEY` |
| 참조 무결성 | 외래키 값은 NULL 이거나 참조 릴레이션의 기본키 값과 같아야 한다 | `FOREIGN KEY` |
| 도메인 무결성 | 속성 값은 정의된 도메인에 속해야 한다 | 타입, `CHECK`, `DEFAULT` |
| 사용자 정의 무결성 | 사용자가 정의한 업무 규칙을 만족해야 한다 | `CHECK`, 트리거 |
| NULL 무결성 | 특정 속성은 NULL 이 될 수 없다 | `NOT NULL` |
| 고유 무결성 | 특정 속성의 값은 서로 달라야 한다 | `UNIQUE` |

---

# 무결성 — 위반 사례

| 실행 | 위반 |
| --- | --- |
| `INSERT INTO 학생 (학번, 이름) VALUES (1001, '중복')` | 개체 무결성 |
| `INSERT INTO 학생 (학번, 이름, 학과코드) VALUES (2000, '참조', 'D99')` | 참조 무결성 |
| `INSERT INTO 학생 (학번, 이름, 학년) VALUES (2000, '학년', 5)` | 도메인 무결성 |
| `DELETE FROM 과목 WHERE 과목코드 = 'C101'` | 참조 무결성 |

- 참조 무결성은 **자식에 삽입할 때**뿐 아니라 **부모를 삭제·수정할 때**도 검사한다
- 학과코드가 NULL 인 학생(윤아름)은 참조 무결성 위반이 아니다

# 시스템 카탈로그

DBMS 가 스스로 생성하고 유지하는, 데이터베이스 개체에 대한 정보를 담은 시스템 테이블.

- **데이터 사전**(Data Dictionary)이라고도 한다
- 카탈로그에 저장된 정보를 **메타데이터**라고 한다
- 사용자는 SQL 로 조회할 수 있지만 **직접 갱신할 수는 없다**
- DDL 을 실행하면 DBMS 가 자동으로 갱신한다

```sql
SELECT TABLE_NAME, TABLE_ROWS
FROM information_schema.TABLES WHERE TABLE_SCHEMA = 'study';

SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE
FROM information_schema.TABLE_CONSTRAINTS WHERE TABLE_NAME = '학생';
```

- MySQL 에서는 `information_schema` 가 시스템 카탈로그 역할을 한다

# 정리 — 서술형 답안 키워드

| 질문 | 답 |
| --- | --- |
| 속성의 수 / 튜플의 수 | 차수(Degree) / 카디널리티(Cardinality) |
| 유일성만 만족 / 유일성과 최소성 만족 | 슈퍼키 / 후보키 |
| 후보키 중 기본키가 아닌 것 | 대체키 |
| 기본키는 NULL·중복 불가 | 개체 무결성 |
| 외래키는 NULL 또는 참조 기본키 값 | 참조 무결성 |
| 스키마 3계층 | 외부, 개념, 내부 |
| DBMS 필수 기능 | 정의, 조작, 제어 |
| 설계 순서 | 요구 분석 → 개념 → 논리 → 물리 → 구현 |
